# Auditoria — SIGAA-ME

Verdict: Not approved

Audited by Claude Opus 5

## Resumo

O núcleo de fronteira do app está bem feito: IPC nomeado e validado, política de
remetente, CSP, sanitizador de notícia, isolamento por conta, coordenador de
sessão. As regras invioláveis do `CLAUDE.md` são cumpridas — zero `innerHTML`
com dado externo, zero `any` na fronteira, zero fallback de credencial, zero
`console` fora do logger.

O que reprova está todo no caminho de download, e é o mesmo padrão três vezes: o
**nome** do arquivo é usado como identidade onde o **id** é a chave real, e um
erro de escrita sai por um caminho diferente de todos os outros erros.
Resultado: arquivo baixado apagado em silêncio, lote inteiro abortado por uma
falha de disco, e `[object Object]` na tela do usuário.

## Top 3

### 1. Broken — `electron/services/http-scraper.service.ts:956`

```ts
writer.on('error', async (err) => {
    log.error('File write error.', { error: err });
    await descartarParcial('erro de escrita');
    reject({ success: false, error: err.message });
});
```

Todos os outros caminhos de falha de `downloadFile` **resolvem** com
`{ success: false, error }`. Este **rejeita** — e rejeita com um objeto simples,
não com um `Error`.

Duas consequências, ambas confirmadas:

- Em `downloadAllFiles`, a rejeição estoura o `await` da linha 464 e cai no
  `catch` da linha 577, que aborta **o lote inteiro**. Os arquivos já baixados
  com sucesso somem do relatório, o retry e o fallback Playwright não rodam, e o
  usuário recebe uma única falha global. O contrato de todo o resto do laço é
  "este arquivo falhou, próximo".
- A mensagem passa por `errorMessage(error)` (`shared/errors.ts:105`), que faz
  `String(error)` em não-`Error`: o usuário vê **`[object Object]`** e
  `classifyMessage` devolve `UNKNOWN`. É a mesma regressão que o `BUG-006`
  fechou, reaberta por outra porta.

Gatilho: qualquer erro de escrita em disco — `ENOSPC`, `EPERM` do antivírus
segurando o handle, pasta de downloads num drive removível que sumiu.

Correção: `resolve({ success: false, error: err.message })`, como todos os
outros ramos. Se algo precisar mesmo propagar, que seja um `Error`.

### 2. Broken — `electron/services/file-validation.service.ts:231`, disparado por `electron/services/sigaa.service.ts:357`

`finalizeDownload` fecha com `fs.promises.rename(partPath, filePath)`, e
`rename` sobrescreve o destino sem avisar. O filtro de duplicata de
`downloadAllFiles` (linhas 357–375) roda **uma vez, antes do laço**, checando
`fs.existsSync` do caminho final: ele detecta arquivo que já estava no disco,
nunca arquivo que este mesmo lote acabou de gravar.

Dois arquivos da mesma turma cujo nome sanitizado coincide passam os dois pelo
filtro, baixam os dois, e o segundo **renomeia por cima do primeiro**. O
relatório diz `downloaded: 2`; o disco tem 1 arquivo. Nada avisa o usuário.

Três formas de colidir, todas verificadas contra o código real:

- nomes idênticos em tópicos diferentes da turma (ids diferentes, nome igual);
- nomes com mais de 150 caracteres que só diferem depois do corte de
  `sanitizeSegment(raw, 150)`;
- nomes que diferem só num caractere inválido no Windows — `Lista:1.pdf` e
  `Lista/1.pdf` viram ambos `Lista_1.pdf`.

O `.part` intermediário colide igual (`http-scraper.service.ts:895`), então dois
downloads simultâneos do mesmo nome também se corromperiam; hoje não acontece só
porque o laço é sequencial.

Correção: desambiguar no destino, não na origem. Ao montar o caminho final, se
ele já existe — no disco ou já usado neste lote — acrescentar sufixo `(2)`,
`(3)`; e usar `file.id` na chave de duplicata, não o nome.

### 3. Broken — `electron/services/sigaa.service.ts:498`, `:523`, `:561`

Os três reencontros de arquivo depois da primeira passada usam o **nome** como
chave, enquanto `findScript` (linha 50) já documenta que o **id** é a única
chave legítima ("o nome que acompanha o pedido nunca seleciona qual script
executar"):

```ts
.map(r => files.find(f => f.name === r.fileName))                // :498  fila de retry
const index = results.findIndex(r => r.fileName === file.name);  // :523  onde gravar o resultado
const originalFile = files.find(f => f.name === fileName);       // :561  fallback Playwright
```

Com dois arquivos de mesmo nome no lote e o segundo falhando, a linha 498
devolve o `DownloadFileRef` do **primeiro** — o retry rebaixa o arquivo que já
tinha dado certo. A linha 523 marca `downloaded` no registro do primeiro, que já
estava `downloaded`; o registro do que falhou fica `failed` para sempre, e o
contador `failed--` dessincroniza do array `results`. A linha 561 repete o erro
no fallback Playwright.

Não é o mesmo bug do achado 2: este erra mesmo quando os dois arquivos vão para
caminhos distintos, porque o pareamento acontece antes de qualquer caminho.

Correção: carregar `DownloadRecord` com o `id` do `DownloadFileRef` e parear por
id nos três lugares.

## Todos os achados

**Broken**

- Broken `electron/services/http-scraper.service.ts:956` — `reject` num objeto simples onde todo o resto resolve: aborta o lote inteiro e mostra `[object Object]` ao usuário.
- Broken `electron/services/file-validation.service.ts:231` (via `sigaa.service.ts:357`) — `rename` sobrescreve; dois arquivos de nome sanitizado igual no mesmo lote deixam um só no disco, com relatório de sucesso para os dois.
- Broken `electron/services/sigaa.service.ts:498`, `:523`, `:561` — retry e fallback pareiam arquivo por nome em vez de id; com nomes repetidos, rebaixam o arquivo errado e marcam o registro errado.

## Ordem recomendada

1. **`http-scraper.service.ts:956`** — uma linha, `reject` → `resolve`. Maior
   dano pelo menor diff: hoje uma falha de disco num arquivo derruba o lote
   inteiro.
2. **Identidade por id no caminho de download** (`sigaa.service.ts:498,523,561`
   e a chave de duplicata em `:357`). Os achados 2 e 3 têm a mesma raiz;
   consertar o pareamento primeiro deixa o passo 3 menor.
3. **Desambiguação do caminho final** em `finalizeDownload`. Fecha a perda de
   dado que sobra depois do passo 2.
4. **`download.service.ts:82`** — `return false` no `catch`: falha ao
   inspecionar deve forçar download novo, nunca declarar sucesso.
5. **Electron 30 → versão suportada.** Único achado fora do domínio do download
   e único que piora sozinho com o tempo.
6. Os dois documentos que mentem (`ARCHITECTURE.md:124`, `README.md:85,73`) —
   quinze minutos, e param de induzir o próximo leitor ao erro.
